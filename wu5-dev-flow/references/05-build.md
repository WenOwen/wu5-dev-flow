# 05 开发：一个可验收的纵向切片

在实现、修复或重构任务时读取。前提是本次目标、产品范围和必要的技术边界已清楚。

## 值得保留的见解

- **任务大小决定审查质量。** “加入认证”过大，“完成邮箱登录并返回会话”更可检查。目标是一个能验证、能解释差异、能恢复的结果；文件数不是原子性的唯一判断。
- **先明确做法，再实现。** 对复杂任务先写短计划，说明影响位置与验收方式。沿用现有选型与授权，只有关键决定缺失或范围扩大时才提问，不每次重复审批。
- **纵向切片减少接口猜测。** 把一条用户路径的必要 UI、接口、数据和测试接通，再扩下一条；不要先建完所有页面，再发现后端的数据与权限不同。
- **先找已有实现与共享工具。** Agent 不知道某个 helper 的存在就容易复制。修改前检索相似逻辑，结束时核对是否引入重复状态、不必要依赖或范围外文件。
- **演示后的工作要预留。** 边界、失败状态、集成和环境差异通常比生成主路径更费力，不能把能演示当成能交付。
- **Bug 多次修不好时，改变观察方式。** 从用户动作沿数据流定位首次偏离，列假设、用最小测试或日志证伪，再修根因。看不懂 Bug 时直接大重构，可能只把它搬到别处。
- **小提交保留可用恢复点。** 检查、差异审查、任务提交与交接形成闭环。上下文已混乱时换会话，而不是强制每个小任务都开新聊天。

## 执行与交接

从一个验收条件开始；可测试行为先 RED，再最小实现、GREEN 和必要重构。工具错误不能冒充 RED。运行受影响检查后审查最终差异，核对暂存内容与已验证内容一致，再提交本任务。

任务清单、实际结果和下一步只写 memory。改变产品行为读 PRD 阶段；改变技术方案读 TechDesign 阶段；测试通过但用户路径不通，转质量阶段检查测试层级。
