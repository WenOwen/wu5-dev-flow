# 06 质量：检查结果，而非生成过程

在变更收口、准备发布、结果与测试矛盾或风险较高时读取。

## 值得保留的见解

- **测试可能测错层。** 只验证实现内部结构，可能在功能已坏时仍通过。至少沿主要用户路径检查真实输入、集成边界和可观察结果，手工验收也可作为明确证据。
- **作者会受已有结论影响。** 重新从需求与原始差异审查，而不是让实现解释为自己背书。有授权且可用时，可用独立人或 Agent 复审；没有独立复审就如实记录。
- **先需求，再质量。** 核对用户行为、非目标和技术约定，再看正确性、类型、异常、安全、依赖与可维护性。文档也检查读者与职责，格式和字数不能证明内容正确。
- **正常、边界、失败是覆盖维度。** 按风险选择测试数量，不固定“三个测试”。关注空输入、重复动作、未授权访问、外部失败以及本次涉及的并发状态。
- **错误处理必须留下可观察结果。** catch 应有实际恢复、给用户明确失败，或保留可诊断的信息；吞掉异常会制造“运行正常”的假象，日志同时避免泄露敏感信息。
- **依赖与类型问题要追根。** 核实所用 API 和实际版本，先修根类型或契约，避免用忽略指令、宽泛类型或关掉规则掩盖问题。
- **删除密钥不等于消除泄露。** 若确认泄露，先撤销或轮换，再处理历史与影响。扫描应检查文件和历史内容；`git log --grep` 只找提交说明，不能当作历史密钥扫描。

## 执行与交接

运行项目已配置且适用的测试、类型、lint、构建与安全检查；工具缺失、旧失败和新增失败分别记录。不要把无关环境故障改成通过，也不要为凑检查擅自安装工具。

用实际命令、版本或改动范围、结果与未解决风险支撑完成结论。主要用户路径通过且符合需求后才进入发布；细节指向测试或提交，简短摘要写 memory。
