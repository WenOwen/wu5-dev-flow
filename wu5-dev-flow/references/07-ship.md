# 07 技术发布：在真实目标验证候选版本

在打包、部署、发布版本或排查目标环境故障时读取。

## 值得保留的见解

- **本地成功仍可能包含环境假设。** 核实运行版本、配置作用域、外部服务、权限、文件系统和迁移步骤；构建成功不能替代目标环境冒烟。
- **交付形态决定发布方式。** 服务看真实环境，移动应用看实际测试构建，CLI 和库看安装执行，技能看安装目录与真实调用；不要求每个项目都有在线 URL。
- **先准备看见失败的办法。** 根据项目选择错误日志、健康检查、试用反馈或用户行为观察。确需录屏时处理授权与敏感数据，不能自动给所有项目安装追踪工具。
- **发布绑定版本。** 说明候选提交或制品、包含的能力、配置、已知风险和恢复方式。技术合并、部署成功、冒烟通过与用户通知分别记录。
- **早验证交付，不必等到完美。** 在核心流程可靠后尽早让真实用户试用，先有可用结果再决定该打磨什么。提前打包或预览不等于获得生产发布授权。
- **线上失败先看证据。** 从错误日志和环境差异排查，不凭模型猜测再盲目部署。发布失败时按已授权的恢复方式处理；数据变化的恢复不能假设回退代码即可完成。

## 执行与交接

发布前确认质量结果仍对应候选内容，准备适用的发布、冒烟和恢复步骤；按已有授权执行。平台审核、测试人数、配额等会变化的规则在实际发布时查官方资料。

```markdown
# 发布：0.1.0
## 候选与状态
commit abc1234；准备完成，尚未部署。
内容：登录、打卡、连续天数。
## 验证与风险
候选测试与构建通过；目标环境登录回调待验证。
## 执行与恢复
现有流水线部署；检查登录→打卡→刷新→重复打卡。
失败恢复上一制品；数据变化先明确兼容与恢复方式。
## 用户交付
提供打卡说明与项目反馈入口。
```

结果更新到 release；实际目标验收通过后进入用户交付。
