# 03 TechDesign：先定核心能力，再选其余层

在新产品选型、引入关键服务或迁移技术栈时读取。产物是面向技术读者的 docs/TechDesign.md。

## 值得保留的见解

- **从 PRD 出发。** 先读用户流程和交付形态，写实现该产品的技术选择；不能把一次修复的操作和验收清单当作技术设计。
- **核心引擎往往比框架更重要。** 地图、支付、搜索、ML 或实时服务可能决定能力边界、成本与后续结构，先评估这个关键选择，再选 Web、移动端、CLI 或技能的载体。
- **每项选择附一句理由。** 不留下“以后再决定”让模型临时挑技术。已确定的选择保持稳定；真正的未知用最小实验验证，记录仍待验证的限制。
- **质疑不必要的层。** 不需要账号或共享数据时，本地存储可能足够；不要为填模板自动增加数据库、身份系统或复杂组件库。
- **成熟方案降低非产品风险。** 优先现有工具、已知兼容版本和必要依赖。迁移已有技术前明确收益、受影响用法和恢复方式，不用换栈逃避难以定位的 Bug。
- **交付路径提前试通。** 先验证构建、预览或打包，避免发布日第一次发现部署困难。连接外部平台与生产自动部署仍需已有授权。
- **实际版本的文档胜过模型记忆。** 读取依赖声明和官方 API 文档；已有文档工具可以使用，不为流程强制安装特定 MCP。

## 执行与交接

说明选型、理由、必要的数据模型与交付方式；接口边界要明确输入、输出、失败与副作用。已有项目小修复沿用 TechDesign，任务细节写 memory。本阶段到此停止：汇报选择与未知项，确认后再进入开发循环，不在同一回合开始实现，用户未授权时不连跳。

```markdown
# TechDesign：RunStreak
## 框架与 UI
Next.js App Router，便于 Web 交付；Tailwind + shadcn/ui 覆盖单页界面。
## 数据与登录
Supabase 提供 Postgres 和身份认证。
## 数据模型
runs：id、user_id、run_date、created_at。用户与日期联合唯一；按用户时区确定日期，连续天数由记录计算。
## 部署
Vercel，连接 Git 仓库构建部署。
```
