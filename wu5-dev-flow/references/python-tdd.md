# Python TDD

## 循环

对每项可测试行为执行：

1. 从需求 ID 选择一个场景。
2. 在项目现有测试布局中编写最小测试。
3. 运行最窄范围 pytest 并观察预期失败；测试错误、导入错误或无关失败不算 RED。
4. 编写使测试通过的最小实现。
5. 运行目标测试获得 GREEN。
6. 仅在全绿状态重构，再运行受影响测试。
7. 运行完整配置的 pytest、pyright；项目启用 ruff 时运行 ruff。
8. 记录证据后创建原子提交，不提交已知红灯。

实现最小代码时仍须遵守 [禁止 Hardcode](hardcode-policy.md)：环境值与业务策略走配置，领域不变量使用命名常量，时间、随机和外部边界使用依赖注入。

## 测试层级

- 纯业务逻辑优先单元测试。
- API、数据库、文件、网络和进程边界增加集成或契约测试。
- 只 mock 外部边界，不 mock 被测对象内部实现。
- 老项目重构前先锁定公开函数、API、文件输入输出和重要副作用；特征测试描述现状，不宣称现状正确。

## 质量规则

- 每个新增或修改需求 ID 至少映射一个测试。
- 不追求统一覆盖率数字；已有 coverage 时不得下降。
- pytest 与 pyright 是必需门禁；ruff 仅在项目已配置时启用。
- 缺少工具时停止并申请依赖批准，不自动安装。
- 疑似 flaky 测试最多重复三次；结果不一致时记录为不稳定。新增不稳定性仍阻塞完成。
- 历史稳定失败记录到 `baseline/debt.md`，新变更不得增加失败数量或扩大失败范围。
- 为配置缺失、非法配置和注入边界编写测试，避免用写死的“默认成功值”掩盖错误。
