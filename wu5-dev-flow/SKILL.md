# Wu5 Dev Flow

先明确要解决的问题，再交付一个可验证的小结果。流程服务于开发，每次只推进当前需要的阶段。

## 接手

读取适用的 `AGENTS.md`，检查工作区，再读已有的 `docs/memory.md` 和与任务有关的文档、代码、测试。核实记录与现状；缺失文档不阻塞明确的小修改。先用一两句话说明当前目标和下一步。

- 新项目：确认用户、问题和最小范围，再选技术与创建工程。
- 老项目：先识别产品目标与既有技术方案，再限定本次改动；沿用结构与工具。
- 只读请求：只分析，不创建文档或改代码。
- 已授权的工作继续完成；只有关键选择缺失或范围改变时才提问，不设置固定审批口令。

## 项目文档

沿用已有等价文档；新建时用下面的路径，按需创建，不批量铺空文件。写文档时参考 [短文档样例](references/documents.md)。

| 文件 | 只回答 |
| --- | --- |
| `docs/research.md` | 问题是否值得解决？有什么依据？ |
| `docs/PRD.md` | 面向需求读者：为谁做、做什么、不做什么、怎样验收？ |
| `docs/TechDesign.md` | 面向技术读者：选什么技术、为什么、数据模型与交付方案？ |
| `docs/memory.md` | 当前做到哪、关键决定是什么、下一步做什么？ |
| `docs/release.md` | 哪个版本、如何发布与恢复、实际结果如何？ |
| `AGENTS.md` | 项目命令、稳定约束、上下文入口。 |

本技能新建的每份项目文档 **不超过 500 字**，按非空白字符计，标题、命令和链接也计入，写完检查长度。写短句和具体结论；删掉重复与过期内容，用链接指向代码、测试、提交或外部来源。不得靠拆分文件绕过限制。已有长文只修改相关内容，保留原有规则；新增的技能说明块也遵守限长。

`PRD.md` 用非技术语言描述用户、产品范围和验收，`TechDesign.md` 根据需求说明技术选择与理由；本次任务、计划和验收结果写入 memory。写 TechDesign 前读 PRD；修复未改变产品技术方案时，无需创建或修改 TechDesign。两份产品文档独立维护，每份不超过 500 字。

落盘前先检查内容是否符合该文档的读者与职责、是否与 PRD 一致，再检查格式和字数。`memory.md` 只留本轮任务、最新验证、未解决问题与少量有效决定，完成后压缩；历史查 Git。

用户要求旧版项目接入新版时，按样例中的接入说明提炼 `spec/`，更新旧技能管理的 AGENTS 说明块；不再运行旧 CLI。

## 选择当前阶段

| 阶段 | 行动与完成条件 |
| --- | --- |
| 环境 | 核实运行、测试和构建入口，沿用可用工具。 |
| 调研 | 查当前证据，写来源、日期和未知项；能说明继续做的理由。个人工具可核实自己的实际痛点。 |
| PRD | 收敛一个核心用户流程，写 MVP、非目标和可观察的成功标准。 |
| TechDesign | 根据 PRD 写产品的技术栈、选型理由、数据模型和部署或分发方式；确认核心流程可由该方案实现，关键未知先做小实验。 |
| 上下文 | 按需补充 AGENTS 的命令与入口、memory 的任务与下一步，让新会话能接手。 |
| 开发 | 执行下面的小循环，一次完成一个验收场景。 |
| 质量 | 对照验收标准审查最终差异，运行适用的回归、类型、lint、构建与关键用户流程检查。 |
| 发布 | 准备版本、配置、发布与恢复步骤；执行后检查真实目标环境，记录结果。 |
| 用户交付 | 给出简短使用说明、变更摘要和反馈入口；只在已有文档中补充必要内容。 |
| 迭代 | 从真实反馈挑一个问题，明确预期改善与验证方法，再进入相关阶段。 |

新项目走完整主线；小修复从复现进入开发；重构先锁定现有行为；发布请求先核实候选版本。每次不重做调研或重写所有文档。

## 最小开发循环

1. 从产品目标或缺陷选择一个能验收的小任务，复杂变更在 memory 写短清单，沿用已有技术设计。
2. 对可测试行为先写测试并运行，观察预期失败（RED）。工具缺失、导入错误、无关失败不算 RED。
3. 写最小实现使测试通过（GREEN）；需要重构时保持测试通过。
4. 跑受影响检查，审查最终差异。文档、样式等改动采用对应检查，不制造无意义测试。
5. 在当前开发授权内创建本地原子提交，使用 `type(scope): 中文说明`。只暂存本任务文件，核对暂存内容确实经过验证；提交候选变化后重跑相关检查。
6. 更新 memory 的结果和下一步，继续下一任务；完整变更结束时再做质量收口。

验证摘要写实际命令、结果及对应任务或版本。未运行就写未运行；旧失败与本次新增失败分清。检查失败或无法执行时说明影响，不宣称已验证完成。

## 交付边界

保护用户已有改动；脏工作区不自动停止，也不 stash、reset 或覆盖。按项目约定使用短分支。配置沿用现有机制，敏感值不进入代码、文档或提交，避免为简单常量制造配置系统。

推送、PR、合并、部署、对外通知和不可逆数据操作按用户已有授权执行；尚未授权时先完成可审查的准备。缺少检查工具先说明缺口，不为流程擅自更换工具链。部署后验收失败时按已授权的恢复方案处理，否则报告并请求所需授权。

完成时简述改了什么、实际验证结果、遗留问题和下一步。只有目标环境验收通过才能说已发布；反馈不足时不宣称效果已证实。
